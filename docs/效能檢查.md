## 首次載入實際下載了多少

首頁程式在畫完之後用 `setTimeout` 呼叫 `lmLoad()`，而 `lmLoad()` 會 `fetch('law_map.json')`。空的新環境沒有作答紀錄，弱點章節算完是空的，但檔案仍整份下載。另外 `sw.js` 安裝時用 `cache: 'reload'` 把 `./`、`index.html`、manifest、四張圖、`law_map.json` 再抓一次。

這次用乾淨的 Chrome 使用者目錄，關掉 HTTP 快取，在 loopback 記 CDP `Network.loadingFinished` 的 `encodedDataLength`（含回應標頭）。13 個請求，加總 **10,038,492 bytes**。

| 誰發的 | 網址 | encodedDataLength |
| --- | --- | ---: |
| 頁面 | `/` | 2,115,730 |
| 頁面 | `/law_map.json` | 1,830,160 |
| 頁面 | `/manifest.webmanifest` | 493 |
| 頁面 | `/icon-512.png` | 7,342 |
| 頁面 | `/icon-192.png` | 2,647 |
| service worker | `/` | 2,115,730 |
| service worker | `/index.html` | 2,115,730 |
| service worker | `/law_map.json` | 1,830,160 |
| service worker | `/manifest.webmanifest` | 493 |
| service worker | `/icon-512.png` | 7,342 |
| service worker | `/icon-192.png` | 2,647 |

| service worker | `/apple-touch-icon.png` | 2,676 |

也就是 HTML 傳了 3 次（頁面的 `/`，加上 service worker 的 `/` 和 `/index.html`），`law_map.json` 傳了 2 次。三次 HTML 的 encodedDataLength 合計 6,347,190；兩次 law_map 合計 3,660,320；其餘圖示與 manifest 合計 30,982。

頁面 performance API 在同一輪看到的本體（不含 service worker 那份、不含標頭）是：

- 文件 2,115,490
- law_map.json 1,829,913（耗時 196ms，開始於導覽後 341ms 左右）
- manifest 256
- icon-512 7,167
- icon-192 2,472

這五項本體合計 3,955,298 bytes。文件本身：TTFB 176ms、回應結束 228ms、DOMContentLoaded 388ms、load 389ms。這是 loopback，不能當成手機網路的時間。

`sw.js`（1,583 bytes）沒有出現在這份 CDP 清單裡，所以沒有把它加進 10,038,492。service worker 有安裝成功，快取裡 8 個網址都在，表示腳本有被取得，只是這次事件沒有單列它的位元組。

### 模擬 4G 時，只測到文件那一段

另兩次用乾淨設定檔，套 Puppeteer 內建網路條件。只對得上「文件那一個請求」的時間；service worker 的大量下載沒有把總時間拉長，判斷頁面的網路模擬沒有套到 service worker。因此下面不把 10MB 換算成 4G 秒數。

| 條件 | 下載吞吐（位元組／秒） | 延遲 | 文件 responseEnd | DCL | load |
| --- | ---: | ---: | ---: | ---: | ---: |
| Fast 4G | (9,000,000/8)×0.9 = 1,012,500 | 165ms | 2260ms | 2415ms | 2420ms |
| Slow 4G（同 Fast 3G） | (1,600,000/8)×0.9 = 180,000 | 562.5ms | 12333ms | 12467ms | 12471ms |

這兩輪的頁面 resource timing 裡沒有 `law_map.json`。CDP 只看到 service worker 抓了一次 law_map，沒有看到頁面自己那一次。loopback 那輪兩次都有。所以 4G 條件下「頁面何時拿到 law_map」這次沒有量到。

Slow 4G 的 12333ms 對得上單一 HTML gzip 本體 2,115,490 bytes、吞吐 180,000 bytes／秒（約 11.8 秒）再加延遲。Fast 4G 的 2260ms 同樣只解釋得了那一份 HTML。

## 題庫拆成獨立 JSON、延遲載入

現況：選擇、申論、口訣、主題、章樹、台灣地圖路徑都塞在 `index.html` 的 `<script id="data">`。首頁一執行就 `JSON.parse` 這整段，並且另外再抓整份 `law_map.json`。

1. 把那段 JSON 原樣放到 `bank.json`（本體 6,991,723 bytes，gzip-6 為 2,028,387 bytes）。`index.html` 只留殼。

### 預期效果（估算，沒有改完再測）

- 殼的檔案是 228,886 bytes，Python gzip-6 是 77,687 bytes。現在 Chrome 收到的整份 HTML gzip 本體是 2,115,490 bytes。延遲載入之後，第一次把頁面畫出來之前，HTML 這一段會從約 2.1 MB gzip 降到約 78 KB gzip。
- 題庫改成要用時才抓，那 2,028,387 bytes（gzip-6）從「打開首頁」挪到「開始作答」。
- 若拆開了但仍在首頁立刻把 `bank.json` 抓下來，下載總量幾乎不變：殼 77,687 + 題庫 2,028,387 = 2,106,074，整份 `index.html` 的 Python gzip-6 是 2,106,971，差 897 bytes。
- 首頁現在會讀整份 `D`（題數、今日申論摘要、台灣地圖）。要真的延遲，首頁得改成不依賴這份 JSON，或另備一份很小的摘要。這份報告沒有做那個改動，所以沒有「改完之後的首次載入」實測。
- 就算題庫延遲，只要首頁仍呼叫 `lmLoad()`，第一次還是會下載 `law_map.json` 的 gzip 本體 1,829,913 bytes（這次 Chrome 量到的）。這份檔自己含選擇題本文約 2.20 MB、申論本文約 1.88 MB（未壓縮的欄位值）。題庫拆出去不會拿掉這一包。
- service worker 的 `cache:'reload'` 會把 `./` 和 `index.html` 各抓一次。題庫若仍寫在安裝清單裡，第一次造訪還是會多抓一輪。這也是估算，沒有改 `sw.js` 再量。

## 這次沒跑

- brotli。機器沒有 brotli。
- GitHub Pages 或正式站的回應標頭。數字是本機 gzip 伺服器與檔案本身。
- 模擬 4G 底下「含 service worker 重複下載」的總時間。頁面節流沒有套到 service worker，所以沒有換算。
- 模擬 4G 時頁面自己的 `law_map.json` 何時回來。那兩輪的頁面資源清單裡沒有它。
- `sw.js` 的傳輸位元組。CDP 清單沒有這一筆。
- 改成延遲載入之後的實際首次載入。沒有改程式。
